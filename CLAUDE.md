# Gear generator

Every gear implementation in `lib/geargen/` is generated from a decad-gallery model by the port in `port/`. The gallery
owns each gear's contract, step list, Go model and geometry proof. This repository holds the Fusion side: the dialog,
the Fusion construction calls and what Fusion taught us.

## Goal

The goal is that no gear keeps Fusion construction as stored text. `docs/gallery-translation-goal.md` owns the goal,
the translation rules and the definition of done.

## Which tool regenerates a gear

A gear whose `lib/geargen/<gear>.py` starts with `# Generated by port/cmd/gearport` is generated, and every gear is.
Regenerate it with `gearport gen <gear>` from the repository root (build it with
`go build -C port -o ../.tmp/gearport ./cmd/gearport`). `docs/gallery-port-pipeline.md` describes the pipeline.
`port/go.mod` pins the gallery revision, and `go get` is the only thing that moves it. Bumping the pin is its own change.

A change to the gallery model that touches code the stored fragment follows makes `gearport gen` stop.
Review the fragments under `port/<gear>/fragments/`, then run `gearport accept <gear>` to record the reviewed code.
`gearport id <gear>` prints the build id a deployed file logs when Fusion imports it, so a Fusion run can be matched
to a file.

## Naming

Every sketch, construction plane, axis, timeline feature, body and component a gear creates in Fusion is named by its
role. A name says what the object is for, such as `Driving Crown Scale Anchor 2` or `Pinion Teeth Join`, and carries an
index when it repeats; none keeps Fusion's default (`Sketch12`, `Extrude3`). `solids.name_feature` names a feature and
never fails a build. `tests/test_naming_by_role.py` fails on an unnamed creation in any `lib/geargen/*.py`, including one made through a
local alias such as `extrudes = component.features.extrudeFeatures`. `tests/test_addin_imports.py` compiles every file
under `lib/` and `commands/` and imports the add-in with the Fusion modules stubbed. A gear gets
its names from its fragment, so a new gear's fragment names everything before it is accepted.

## When Fusion gives a verdict

Loading a gear into Fusion is the only check that sees the real thing. What comes back is knowledge that has to be
written down before it evaporates.

The fix never goes into `lib/geargen/<gear>.py`. That file is build output, and the next `gearport gen` overwrites it.
Send the finding to whichever of these fits, then run `gearport gen`:

- A Fusion construction detail of one gear goes in its stored fragment, `port/<gear>/fragments/`.
- A translation rule for a gallery parameter expression goes in `port/fusionexpr`.
- A mapping of gallery names to Fusion names or dialog inputs goes in that gear's `port/<gear>/mapping.go`.
- A behaviour that holds for every gear goes in `docs/fusion/playbook.md` under a `[PB-…]` anchor, and a behaviour of
  one gear in `docs/fusion/<gear>.md` (`spurgear.md` also covers helical and herringbone). Code is better than prose
  where it can express the rule.
- A geometry rule belongs in the gallery model, so ask the gallery to change it.

A verdict that is only remembered in a conversation is lost.

## Ask what the gallery's proof missed

Every Fusion verdict gets one more question: could the gallery's geometry test have caught this? If it could, ask the
gallery to add the case. If it could not, write down why not in that gear's `docs/fusion/<gear>.md`.
