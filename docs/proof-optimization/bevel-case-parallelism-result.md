# Bevel case parallelism — result

Result record for enabling the parallel case runners merged in PR #109 on the bevel gear, following
the execution protocol's completion rules. PR #109's own record is
`docs/proof-optimization/case-parallelism-result.md` on `main`; it added the capability and
deliberately enabled no gear, and this is the enabling change it named as follow-up.

Measured 2026-09-06 on linux/amd64 (WSL2), AMD Ryzen 9 7900X3D, 24 logical CPUs, Go toolchain
resolving `proof/go.mod`, against the engine revisions that file pins. The host is shared and was
not idle; "Measurement conditions" below says what that bounds. Every local figure is the median of
separate `-count=1` runs with its own range beside it.

## Verdict

| Item | Verdict |
|---|---|
| Enable parallel cases for the audited bevel steps | Implemented and accepted. 19 of the 20 `[GO]` steps run their cases together. |
| Whole suite, locally | 1.84x. The suite takes 54.77 s at `-parallel 4` against 100.63 s serial, on non-overlapping ranges. |
| `proof/bevelgear` alone, locally | 2.05x, 47.66 s against 97.65 s, which lands within a percent of #109's independent 2.06x. |
| Whole suite, on CI | 1.11x. The proofs step takes 116 s against 129 s, on non-overlapping ranges. |
| Memory | Not a constraint. The suite's peak resident memory moves from 229.2 MB to 232.5 MB. |
| Races | None. The enabled paths and the whole package pass under `-race` with zero reports. |
| Race run under the default timeout | Now possible. The whole package under `-race` takes 134.26 s here against 756.38 s on `origin/main`, which is past Go's 10-minute default. |
| Coverage | Unchanged. 612 entries either side, 0 verdicts changed, 0 tests lost, 0 skips moved. |
| Naming | One added level, `/cases/`, on the 19 opted-in steps and nowhere else. |
| `stepCircularPattern` | Stays serial. Its build hands seed readings to its assertion outside the case. |
| Concurrency limit | Leave CI's default alone. The runner has 4 CPUs and already chooses 4, which is the best of the three limits measured. |
| Chosen route | The spec asks for it, so `/compile-gear` reproduces the decision rather than reverting it. |

A PR is warranted on these numbers and is open as #110. It is not merged.

The honest shape of the result is that the win is real everywhere and large in only one place. A
developer running `proof/run.sh` locally waits 46 seconds less. CI saves about 13 seconds on the
proofs step and no billable runner minutes at all, because package concurrency already keeps the
4-core runner busy and case parallelism can only fill the tail.

## Why this did not go through a full `/compile-gear` re-draft

PR #109's record says enabling a gear "belongs to `/compile-gear`". That is right about where the
decision belongs and wrong about which command to run, and running the full re-draft would have
destroyed work.

`stage.py`'s `plan_actions` computes its prune list as every `.go` file in the destination that the
draft does not produce, and `compile-gear/SKILL.md` states the same behaviour at step 4: the
placement deletes "any `.go` file there the draft no longer produces". `classify_destination` does
not stand in the way, because it refuses only a file that is neither the script's own output nor
clean against `HEAD`, and a committed clean file passes that guard.

Two files sit in a proof directory without being named by any step list, both added by `88b1ea4`
(#85): `proof/bevelgear/render_test.go` and `proof/cycloidal/render_test.go`. Nothing in
`compile-gear/prompt.md` mentions render, so no drafter would reproduce them. A full recompile of
`bevelgear` therefore deletes `proof/bevelgear/render_test.go`, with one printed `pruned <path>`
line to show for it.

Beyond that, a re-draft rewrites `spec/bevelgear/steps.md` and all 5,200 lines of
`proof/bevelgear/*.go` from the prose. Case names come from case tables the drafter writes, so the
subtest inventory this change is supposed to preserve would not survive, and the comparison below
would have nothing to compare.

So the decision went into the spec, where it belongs and where the next re-draft will read it, and
only the artifact the scheduling actually decides was regenerated. The prune behaviour is being
raised separately as its own concern; it is not this change's to fix.

## The spec change, and why the decision belongs there

`spec/bevelgear/instructions.md` gains a "Proof Case Scheduling (bevel-specific)" section. It asks
for the parallel entry point for every `[GO]` step, names the Pattern step as the one exception and
says why, and states that a step which acquires a build-to-assertion hand-off moves to the serial
runner in the same change.

The section sits at the end of the file. Every `**From:**` citation in the step list names a line
range in this spec, so a section inserted in the middle would shift the lines under every later
citation; appending moves none of them.

`.claude/skills/compile-gear/prompt.md` gains a paragraph describing the parallel counterparts.
It is capability only. The serial method stays the default for every step, and a drafter writes a
parallel one only where that gear's spec asks, so no other gear's next compile changes. The
`compile-gear` skill forbids gear-specific guidance in that prompt, and this paragraph names no
gear.

With the spec asking for it, the 19 annotations in `spec/bevelgear/steps.md` are what the spec
implies rather than a hand edit that the next regeneration reverts. That reversion is the reason
#109 refused to make the change, and it is what the spec section removes.

## The audit, and what stays serial

`.tmp/audit-package-state.py`, written for #109, scans every gear proof package for package-level
variables assigned from inside a function, in two passes: bare assignment, and mutation through an
index, a field or `append`. It was re-run on this branch and its output is
`.tmp/audit-package-state.txt`.

It reports three things and only one is a finding. `proof/cycloidal`'s four colours are each
reported at their own declaration line, so they are initialisers. The blank identifier `_` in
`proof/bevelgear` is not a write to anything. What is left is the real case:

```
proof/bevelgear/solids_test.go  patternSeedAzimuth
proof/bevelgear/solids_test.go  patternSeedRadius
proof/bevelgear/solids_test.go  patternSeedHeight
proof/bevelgear/solids_test.go  patternSeedVolume
```

`stepCircularPattern` measures the seed solid into those four variables and then retires the seed
with the pattern increment, and `assertCircularPattern` reads them back, because the seed cannot be
measured afterwards. That hand-off leaves the case, so two cases running together overwrite each
other's readings. #109 hit exactly that when it moved every solid step to the parallel runner, and
the failure was loud only because the two gear sides differ in volume; a pair of cases whose seeds
measured alike would have passed on each other's numbers.

`stepCircularPattern` therefore keeps `proofkit3d.RunSolid`. The comment beside those four
variables now says that is why, replacing the sentence that claimed the harness runs one case at a
time, which is no longer true of the package around it.

Nothing enforces the rule for a future step. The audit script is the check, and it is not wired
into any gate; a proof that acquires a build-to-assertion hand-off and stays on the parallel runner
would report a wrong verdict rather than fail. That is stated here as the residual risk rather than
fixed, because wiring a new gate is its own change.

## Coverage and verdicts

The whole suite was run with `-json` on `origin/main` and on this branch, and the two inventories
were compared by `(package, test)` and final action. `.tmp/compare_verdicts.py` is the comparison,
`.tmp/baseline-suite.jsonl` and `.tmp/candidate-suite.jsonl` are the runs it reads, and
`.tmp/verdict-compare-suite.txt` and `.tmp/verdict-compare-bevelgear.txt` are its output.

Two normalisations are applied, and they are applied to **both** sides. A `cases` segment sitting
immediately below a top-level test name is removed, and the grouping entries themselves, whose whole
name is `Test.../cases`, are dropped. Both sides, because `origin/main` already carries 14 grouping
subtests of its own: #109's harness fixtures are written on the parallel runners, so a rule applied
to the candidate alone reports every one of them as moved. Applying it to one side only was the
first thing tried, and it produced 56 false "missing" and 42 false "added" entries, all of them in
`proofkit` and `proofkit3d`.

| Check | Whole suite | `proof/bevelgear` |
|---|---|---|
| Baseline entries | 612 | 198 |
| Candidate entries | 612 | 198 |
| Passes, baseline against candidate | 596 against 596 | 188 against 188 |
| Skips, baseline against candidate | 16 against 16 | 10 against 10 |
| Missing from candidate | 0 | 0 |
| Added beyond the grouping subtests | 0 | 0 |
| Verdicts changed | 0 | 0 |
| Package-level verdicts changed | 0 | 0 |
| Grouping subtests, baseline against candidate | 14 against 33 | 0 against 19 |

The 19 new grouping subtests are exactly the 19 opted-in steps, one each. No test was lost, no
verdict moved, and no skip appeared or disappeared.

The one filter the repository documents is unaffected. `CLAUDE.md` gives
`proof/run.sh --package ./bevelgear -- -run '^TestGearProfiles$' -count=1`, and Go applies each
`/`-separated part of a `-run` expression to one subtest level, so a single-part expression selects
top-level tests and runs everything beneath them. Run on this branch, that filter passed with all 16
cases executing under `TestGearProfiles/cases/`. A filter naming a case explicitly, such as
`-run 'TestGearProfiles/lattice_1'`, would need `cases/` inserted; none is written down anywhere in
the repository.

## Measurement

Four arms, interleaved by round, three samples each: the serial baseline at `origin/main`, and this
branch at case concurrency 1, 2 and 4. Every arm holds `GOMAXPROCS=8`, package concurrency `-p 8`,
the same engine pins and `-count=1`. Wall time, CPU and peak resident memory all come from
`/usr/bin/time -v`. `.tmp/measure.py` is the driver, `.tmp/measure/suite-samples.jsonl` and
`.tmp/measure/bevel-samples.jsonl` hold every sample, and each sample's own `time -v` file sits
beside them.

### The whole proof suite, locally

This is the arm the decision rests on, because it is the one where the other nine packages are
already running beside `bevelgear`.

| Arm | n | Median | Range | CPU | Peak RSS | Against serial |
|---|---|---|---|---|---|---|
| `serial-baseline` | 3 | 100.63 s | 89.03 – 104.33 s | 303% | 229.2 MB | 1.00x |
| `parallel-1` | 3 | 99.75 s | 94.49 – 101.32 s | 303% | 228.7 MB | 1.01x |
| `parallel-2` | 3 | 68.40 s | 64.21 – 69.96 s | 490% | 233.4 MB | 1.47x |
| `parallel-4` | 3 | 54.77 s | 53.40 – 55.18 s | 652% | 232.5 MB | **1.84x** |

The suite takes 54.77 s at `-parallel 4` against 100.63 s serial. The two bands do not overlap and
are not close to overlapping: the serial arm spans 89.03 – 104.33 s and `parallel-4` spans
53.40 – 55.18 s, so the result survives this host's noise by a wide margin. Peak resident memory
moves from 229.2 MB to 232.5 MB, which is 3 MB, so memory is not a constraint at this bound.

`parallel-1` measures 99.75 s against the serial arm's 100.63 s. That difference is 1%, far inside
what this host swings on its own, and nothing is claimed from it in either direction.

|---|---|---|---|---|---|---|
| `serial-baseline` | 3 | 97.65 s | 88.26 – 99.96 s | 137% | 136.7 MB | 1.00x |
| `parallel-1` | 3 | 97.84 s | 96.09 – 98.55 s | 137% | 136.5 MB | 1.00x |

### On CI

Two throwaway branches carried the arms, `measure-ci-serial` off `origin/main` and
`measure-ci-parallel` off this one. Each carried the same two-line edit to the workflow's "Run the
proofs" step: `-count=1`, so the proofs execute rather than being served from Go's test cache, and
an `nproc` line so the runner size is on the record. Nothing else differed between them, and neither
branch is for merging. Three pairs were dispatched, one pair at a time.

The runner reports **4 CPUs**, so `go test` there already defaults `-p` and `-parallel` to 4. CI is
therefore running at the same case concurrency this document recommends, without the workflow asking
for it.

| Arm | n | "Run the proofs" median | Range | Job median | End-to-end median | Runner minutes |
|---|---|---|---|---|---|---|
| serial | 3 | 129 s | 128 – 130 s | 152 s | 153 s | 9 |
| parallel | 3 | 116 s | 116 – 127 s | 144 s | 144 s | 9 |

The proofs step drops from 129 s to 116 s, which is 1.11x and about 13 seconds. The ranges do not
overlap, so the gain repeats, but it is a tenth of what the same change buys on an idle-ish
24-core host. Billable runner minutes are 9 either way, because the proof job stays inside the same
whole-minute bucket and the six other jobs are unchanged.

Run ids: serial `34027214754`, `34027374902`, `34027530589`; parallel `34027215904`,
`34027376414`, `34027531838`. `.tmp/ci-timing-samples.txt` holds the collected output.

### Why CI gains so much less

The suite runs its packages concurrently before any case runs concurrently. On the 4-CPU runner
`-p 4` already keeps four packages in flight, so the cores are busy from the start and case
parallelism can only fill the tail, once the shorter packages have finished and `bevelgear` is the
only one left. On a 24-core host with `GOMAXPROCS=8` there is idle capacity throughout, and case
parallelism uses it.

This is why the local 1.84x, and #109's isolated 2.06x on the bevel package, do not establish a CI
benefit. The CI number is the one that describes CI, and it is 1.11x.

### The concurrency limit

**Leave CI's default alone, which is 4 on the current runner.** Of the three limits measured, 4 is
the best locally by a clear margin and is what the runner already chooses, so no workflow change is
needed and none is made. A limit set explicitly in the workflow would freeze the case concurrency at
a number that stops tracking the runner, and there is nothing in these results to pay for that: the
gain is already bounded by the cores, not by the limit.

Nothing here suggests 4 is a ceiling on a larger host. It is where this was measured, and no higher
bound is claimed.

### Bevel is no longer the suite's longest package

The handoff run of `proof/run.sh`, which uses Go's own default `-parallel` on this 24-CPU host,
reports these per-package times:

```
bevelgear        27.658s
cycloidal        50.448s
spurgear         36.457s
helicalgear      32.036s
herringbonegear  21.986s
```

`cycloidal` is now the longest package by a wide margin, and `bevelgear` is the fourth. That
reverses the position #109 recorded, where `bevelgear` was the critical path and the reason to do

gain is unmeasured here.

## Measurement conditions

The host is shared and was not idle, which is stated here rather than buried, because it bounds what
the local numbers mean.

Six `review-82-pass-12-start-server` processes from `lestrrat-go/server-starter`, about seven days
old at roughly 36% CPU each, and one `codex` process, together hold about 2.6 of the 24 cores. None
is mine and none was killed. The decad session working follow-up F2 held its own measurement window
until 19:15 and confirmed its samples were finished before mine began; two suite runs of mine at
about 18:05 and 18:18 landed inside its window, it was told, and it re-took the three samples that
fell in that span.

The controls that survive a busy host were applied. `GOMAXPROCS` was pinned to 8 and the package
concurrency `-p` to 8 for every local sample, so no arm could take the machine and every arm paid
the same package-level concurrency. Samples never overlapped. Rounds interleave across the four
arms, so drift in the background load lands on all of them rather than on whichever ran last. Every
sample forces execution with `-test.count=1`. Both trees were built before any sample, by a
`-run '^$'` warm pass, so no build time sits inside a measurement.

Wall time, CPU percentage and peak resident memory all come from `/usr/bin/time -v`, so the three
figures for one sample come from one tool rather than from three.

This host produces run-to-run swings on a single package larger than any small difference reported
here. #109 measured the same unchanged binary at 20.11 s and 23.77 s on one test in one session,
and appending an unused, uncalled function to a source file moved another by 3.7 s; the likely cause
is core placement on a Ryzen 9 7900X3D whose two core complexes differ in cache and clock, which
WSL2 hides behind a single reported L3 pool. Anything under about 15% is therefore not attributable
here, and the `parallel-1` arm below is reported on that footing rather than as a regression.

What this does not support is an absolute claim about how long the suite takes on an idle machine.
The comparison between arms holds, because they all paid the same background cost.

### A deliberately failing case still fails

A change that makes cases run together has to be shown still to fail, and to fail on the right case.
Four failures were injected one at a time, each run and then reverted; `.tmp/inject-*.log` holds the
output.

| Injection | Where | Result |
|---|---|---|
| Assertion fails for one sketch case | `stepResolveInputBounds`, on `proofkit.RunParallel` | only `module_2_driving_19_pinion_13` failed, the other 11 cases passed |
| Assertion fails for one solid case | `assertToothProfile`, on `proofkit3d.RunSolidParallel` | only the two `tooth_spacing_1mm` cases failed, the other 8 passed |
| Build fails for one solid case | `stepToothProfile`, on `proofkit3d.RunSolidParallel` | same two cases failed, the other 8 passed |

on a real gear.

### The race check needs a raised timeout, and this change is why it may stop needing one

#109 recorded that the whole `proof/bevelgear` package under `-race` exceeds Go's default 10-minute
test timeout on `origin/main`. That was measured here rather than carried over, by running the same
command against both trees with `-timeout 40m`:

| Tree | Whole package under `-race` |
|---|---|
| `origin/main`, serial | 756.38 s, which is 12.6 minutes |
| this branch, parallel | 134.26 s |

Both pass and neither reports a race. The serial figure sits 2.6 minutes past the default timeout,
which confirms #109's claim as a measurement rather than a citation, and the parallel figure sits
well inside it. So a whole-package race run, which is not something anyone can do today without
remembering to raise the timeout, becomes an ordinary `go test -race ./bevelgear/` on this branch.

Every race run in this document still passes `-timeout 40m`, because the baseline arm needs it and
the two arms should differ only in the thing being measured.

## What is not done

**Only `bevelgear` is enabled.** Every other gear still registers serially, and its spec asks for
nothing else, so its next `/compile-gear` reproduces what it has now. `cycloidal` is the package
that becomes the suite's next constraint, and its own gain is unmeasured.

**Nothing gates the rule the spec states.** The audit script is the only check that no other step
carries a reading from its build to its assertion, and it is not wired into `check_compile.py` or
into CI. A future step that acquires such a hand-off and stays on the parallel runner would report a
wrong verdict rather than fail. Wiring that check is its own change.

**`stepCircularPattern` stays serial.** Making its cases independent means carrying the seed
readings per case rather than in package variables, which is an edit to `proof/bevelgear/
solids_test.go`, and that file is compile-stage output. The fix belongs with a compile round rather
than with this change.

**Every figure here is against the currently pinned engines.** The serial arm was measured against
decad `1080cbf4c0a7` and sketch `34765bc10360`. Decad PR #237 is open and cuts `bevelgear`'s serial
wall time in its author's own measurements, so a pin bump lowers the baseline and the ratios above
do not survive that change untested. Re-baseline after the pin moves rather than carrying these
numbers forward.

**The `stage.py` prune is not fixed here.** A full recompile still deletes a hand-written proof file
that no step list names. That is being raised separately, and this change routes around it rather
than repairing it.
