# Cycloidal case parallelism — result

Result record for two things asked as one task: measuring what PRs #110, #111 and #112 did to the
proof suite together, and then enabling the parallel case runners on `cycloidal`, which #110's own
record named as the suite's next constraint.

The two records this continues are `docs/proof-optimization/case-parallelism-result.md` (PR #109,
which added the capability and enabled no gear) and
`docs/proof-optimization/bevel-case-parallelism-result.md` (PR #110, which enabled `bevelgear`).
Both are on `main`.

Measured 2026-09-06 on linux/amd64 (WSL2), AMD Ryzen 9 7900X3D, 24 logical CPUs, Go toolchain
1.26.8 resolving `proof/go.mod`, against the engine revisions that file pins. The host is shared
and was not idle; "Measurement conditions" below says what that bounds. Every local figure is the
median of separate `-count=1` runs with its own range beside it, and every CI figure is the median
of six runs.

## The audit, and why nothing stays serial

A fresh document per case is not evidence of independence, so the audit asked the same five classes
#109 defined, plus document handling, against `proof/cycloidal` on this tree rather than carrying
#109's answer forward. `.tmp/audit_cycloidal.sh` is the scan and `.tmp/audit-cycloidal.txt` is its
output.

| Class | Finding |
|---|---|
| Environment mutation | None. `os.Setenv`, `t.Setenv`, `os.Unsetenv` and `os.Chdir` appear nowhere in the package. |
| Filesystem writes | None. `render_test.go` writes its PNG through `proof/render`, and it is skipped unless `-render.out` names a directory; it registers no harness case and is not a proof. |
| Existing concurrency | None. There is no `go func`, no `sync` import and no `t.Parallel()` in the package. |
| Writes to a `Params` map | Two grep hits, neither a finding. `sketches_test.go:66` is `baseCase` writing its overrides into the map it just made, at table-construction time. `sketches_test.go:322` reads `p[pPinDiameter]` in a comparison and writes nothing. No build and no assert writes the map it is handed. |
| Package-level state written at run time | None. The scan reports `housingColor`, `discColor`, `camColor` and `plateColor`, each at its own declaration line, so they are initialisers rather than run-time writes. |
| Document handling | Every case's document comes from the harness, and the nine `decad.New()` calls in the package are all scratch documents made inside the case that reads them. |

The last row is the one that decides the gear, and it is not luck. decad's `Verify` judges every
pair of live bodies in one document, and a pair it can resolve neither way makes the report
Suspect, which fails the gate. So a step that needs to compare against a body its own Fusion
feature does not leave behind has to measure it in a separate document, and the proof already does
that everywhere. That discipline, adopted for a verification reason, is exactly what makes the
cases independent: there is no reading carried from a build into its assertion anywhere in this
gear, and so nothing for a sibling case to overwrite.

This is the difference from `bevelgear`, where `stepCircularPattern` retires the seed it measures
and has to hand four readings to its assertion through package variables. No cycloidal step retires
an operand it still needs to measure.

## Why this did not go through a full `/compile-gear` re-draft

The scheduling decision belongs to `/compile-gear`, and the command that reproduces it is not the
full re-draft. Two reasons, and the first is about to stop being true.

`stage.py` computes its prune list as every `.go` file in the destination the draft does not
produce, so a full recompile of `cycloidal` deletes `proof/cycloidal/render_test.go`, a
hand-written file added by `88b1ea4` (#85) that no step list names and no drafter would reproduce.
PR #113 is open and fixes exactly that, by recording what staging generated in
`proof/<gear>/stage-manifest.json` and pruning only those files. It is not merged, so it is not on
this branch, and the hazard is live here.

The second reason survives #113. A re-draft rewrites `spec/cycloidal/steps.md` and all 2,400 lines
of `proof/cycloidal/*.go` from the prose. Case names come from case tables the drafter writes, so
the subtest inventory this change exists to preserve would not survive, and the comparison below
that shows no verdict moved would have nothing to compare.

So the decision went into the spec, where the next re-draft reads it, and only the artifact the
scheduling actually decides was regenerated.

## The spec change, and why the decision belongs there

`spec/cycloidal/instructions.md` gains a "Proof Case Scheduling (cycloidal-specific)" section. It
asks for the parallel entry point for every `[GO]` step, states that there is no exception, gives
the scratch-document reason that makes the whole gear safe, and states that a step which acquires a
build-to-assertion hand-off moves to the serial runner in the same change.

The section sits at the end of the file. Every `**From:**` citation in the step list names a line
range in this spec, so a section inserted in the middle would shift the lines under every later
citation; appending moves none of them. The step list's provenance table stamps that file's hash,
so it was restamped with `gen_provenance.py`, and the compile gate accepts the result.

With the spec asking for it, the 26 annotations in `spec/cycloidal/steps.md` are what the spec
implies rather than a hand edit the next regeneration reverts.

than being served from Go's test cache, and an `nproc` line so the runner size is on the record.
Nothing else differed, and none of the branches is for merging. Six rounds were dispatched, one
round at a time, each round dispatching all three arms together.

The runner reports **4 CPUs**, so `go test` there already defaults `-p` and `-parallel` to 4.

### Why CI gains nothing

The package does get faster on CI. Reading one round's per-package times off the two logs:

| Package | `measure-ci-base` | `measure-ci-cyc` |
|---|---|---|
| `cycloidal` | 102.3 s | 74.2 s |
| `bevelgear` | 109.5 s | 101.2 s |
| `helicalgear` | 69.8 s | 75.4 s |
| `spurgear` | 63.1 s | 53.3 s |
| `herringbonegear` | 47.5 s | 54.8 s |

`cycloidal` drops by 28 seconds and the step's wall time does not move, because the four CPUs are
already fully committed. The suite runs its packages concurrently before any case runs
concurrently, and `-p 4` on a 4-CPU runner keeps the cores busy from the first second. Time that
case parallelism frees inside `cycloidal` is immediately taken by whichever package is waiting, so
the totals move around between packages and the sum stays where it was. On a 24-core host with
`GOMAXPROCS=8` there is idle capacity throughout, and case parallelism uses it.

This is the same wall #110 hit. It measured 1.84x locally and 1.11x on CI, and wrote that the CI
gain "can only fill the tail". With `bevelgear` already parallel there is no tail left to fill, so
the second gear gets none of it.

### The concurrency limit

**Leave CI's default alone, which is 4 on the current runner.** The measurement says the gain
appears at 4 and above and is absent at 1 and 2, and 4 is what the runner already chooses, so no
workflow change is needed and none is made. Setting the limit explicitly would freeze the case
concurrency at a number that stops tracking the runner, and there is nothing in these results to
pay for that.

## Measurement conditions

The host is shared and was not idle, which is stated here rather than buried, because it bounds
what the local numbers mean.

Six `review-82-pass-12-start-server` processes from `lestrrat-go/server-starter`, about a week old,
and one `codex` process together hold about 2.6 of the 24 cores. None is mine and none was killed.
The other Claude session working in this repository was asked before the window opened, confirmed
it had nothing running and nothing queued, and held all CPU-heavy work for the duration; the decad
session had already finished its own timing work.

The controls that survive a busy host were applied. `GOMAXPROCS` was pinned to 8 and the package
concurrency `-p` to 8 for every local sample, so no arm could take the machine and every arm paid
the same package-level concurrency. Samples never overlapped. Rounds interleave across the arms, so
drift in the background load lands on all of them rather than on whichever ran last. Every sample
forces execution with `-count=1`. Every tree was built before any sample, by a `-run '^$'` warm
pass, so no build time sits inside a measurement.

This host produces run-to-run swings on a single package larger than any small difference reported
here; the likely cause is core placement on a Ryzen 9 7900X3D whose two core complexes differ in
cache and clock, which WSL2 hides behind a single reported L3 pool. Anything under about 15% is
therefore not attributable, which is why the `-parallel 1` and `-parallel 2` rows are reported as
nothing rather than as a small gain or a small regression.

What this does not support is an absolute claim about how long the suite takes on an idle machine.
The comparison between arms holds, because they all paid the same background cost.

## Reproduction

the revisions `proof/go.mod` pins, pointed at through `SKETCH_DIR` and `DECAD_DIR`. Run
`proof/run.sh` from a worktree rather than the repository root, where a stale `.tmp/go.work` makes
it refuse.

```sh

# The audit that decides which steps may run together. Its output is kept beside it.

# The edit itself: the spec section is appended by hand, then these three reproduce the rest.
```

## What is not done

**Only `bevelgear` and `cycloidal` are enabled.** Every other gear still registers serially, and
its spec asks for nothing else, so its next `/compile-gear` reproduces what it has now. `spurgear`
is the package that becomes the suite's next constraint, and its own gain is unmeasured.

**Nothing gates the rule the spec states.** The audit is the only check that no step carries a
reading from its build into its assertion, and it is not wired into `check_compile.py` or into CI.
A future step that acquires such a hand-off and stays on the parallel runner would report a wrong
verdict rather than fail. #110's record raised this and it is still true; it now covers two gears
rather than one, which makes wiring the check worth more than it was.

**No CI benefit is claimed.** The measurement says the proofs step is unchanged, and the reason it
is unchanged is structural rather than a matter of tuning: on a 4-CPU runner the package
concurrency already saturates the cores. Nothing short of a larger runner, or fewer packages,
changes that. This is worth stating plainly, because the next gear enabled will hit the same wall
and its record should not have to rediscover it.

**The `stage.py` prune is not fixed here.** PR #113 fixes it and is open. This change routes around
it the same way #110 did.

**Every figure here is against the currently pinned engines**, sketch `34765bc10360` and decad
`f200324e2a14`. A pin bump moves the baseline and the ratios above do not survive that change
untested. Re-baseline after the pin moves rather than carrying these numbers forward.
